# Erratum — GGUF Q4_K row geometry (2026-09-16)

## What was wrong

The first `prepare_q4k_exact.py` and the first position-specific PQ script used:

```python
rows = int(t.shape[0])
cols = int(t.shape[1])
```

as though `GGUFReader.ReaderTensor.shape` were NumPy `(rows, cols)` order.

It is not. In current `gguf-py`, `ReaderTensor.shape` is the raw GGML dimension array (`ne[]`):

```text
shape[0] = ne[0] = contiguous matrix row length / GEMV input columns
shape[1] = ne[1] = number of matrix rows / GEMV output values
```

`GGUFReader` separately reverses the dimensions when reshaping the NumPy-backed `t.data` array.

For `blk.0.ffn_gate.weight` the GGUF dimensions are:

```text
ne[0] = 2560
ne[1] = 9216
```

Therefore the real GEMV matrix is:

```text
9216 output rows x 2560 input columns
```

not:

```text
2560 rows x 9216 columns
```

Both interpretations contain the same `23,592,960` logical weights and the same `13,271,040` Q4_K bytes, so byte-count checks did not catch the mistake.

## What remains valid from the legacy runs

The legacy tests still established some representation/arithmetic facts about the byte stream they actually processed:

- direct Q4_K decode agreed with the independently generated reference for the same reinterpreted geometry;
- the managed nibble-LUT path was exactly equal to that direct path;
- the native nibble-LUT path was exactly equal to the scalar Q4_K x Q8_K path for that same reinterpreted geometry;
- the 144 -> 148 byte metadata repack preserved the Q4 nibbles and FP16 `d` / `dmin` values.

Those facts do **not** make the timing numbers valid real-layer Qwen GEMV measurements, because row length and row boundaries affect:

- loop trip counts;
- metadata-decode frequency per output row;
- 4-row / 8-row batching;
- cache behavior;
- output-vector size;
- activation length;
- dynamic LUT layout.

## Results affected

Treat the following as legacy/wrong-row-geometry performance results until rerun with geometry version 2:

- managed `Q4_K EXACT LUT V10` timings (`16.344 ms`, `15.223 ms`, `47.505 ms`);
- the first native `transit_q4k_q8k_native` AVX2/native run using `Rows=2560, Columns=9216`;
- position-specific PQ G16/G8 results generated by the old script orientation;
- any Python reference produced by the old `prepare_q4k_exact.py` with activation length 9216 and output length 2560.

The first native run is retained in `NATIVE-Q4K-Q8K-RESULTS-2026-09-16.md` as historical/falsification evidence only and must not be cited as a real layer benchmark.

## Result not affected

The standalone V15 GGUF parser directly interprets:

```cpp
n    = g.tensor.ne[0];
rows = g.tensor.ne[1];
```

and therefore uses the real `9216 x 2560` GEMV geometry. Its real-Qwen x86 results are not affected by this specific orientation bug.

## Fix

`prepare_q4k_exact.py` now writes:

```text
geometry_version = 2
cols = ne[0]
rows = ne[1]
```

and verifies:

```text
Q4_K bytes == rows * (cols / 256) * 144
activation FP32 count == cols
reference FP32 count == rows
```

`run_transit_q4k_q8k_native.ps1` now defaults to `%TEMP%\q4k_exact_v11`, rejects metadata without `geometry_version >= 2`, and validates all fixture file sizes before compiling/running.

## Required rerun signature

A corrected run for this tensor must begin with approximately:

```text
GEMV matrix      : 9216 rows x 2560 cols
GGUF ne[0]/ne[1] : 2560 / 9216
blocks/row       : 10
```

Any output showing `Rows: 2560` and `Columns: 9216` is the legacy geometry and must not be used for real-Qwen performance conclusions.
