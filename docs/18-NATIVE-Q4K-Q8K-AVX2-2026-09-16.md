# Native Q4_K × Q8_K AVX2 kernel follow-up — 2026-09-16

Status: measured subsystem/kernel result. This is a continuation of PR #16 (`research/ram-lookup-compute-2026-09-16`), not a replacement for Transit DDR3, heterogeneous MoE, or distributed-K3 tracks.

## Scope and evidence boundary

This track answers the next falsifiable gate left by PR #16:

> Can an exact native C/C++ `Q4_K × Q8_K` CPU path beat a current llama.cpp x86 direct-dot baseline on the stock i5-12500H while preserving the original packed Q4_K representation and quantized arithmetic?

It does **not** yet prove an end-to-end llama.cpp/Ollama token/s gain, because current llama.cpp also has repacked Q4_K GEMV paths and other decode work. It also does not prove the same speedup on old Xeon AVX-only servers.

## Test host

```text
CPU: Intel Core i5-12500H
cores / logical processors: 12 / 16
RAM: 16 GiB DDR5-4800
DIMMs: 2 x 8 GiB Samsung M425R1GB4BB0-CQKOL
OS/shell: Windows / Windows PowerShell x64
compiler: Strawberry MinGW-w64 GCC 13.2 g++
flags: -O3 -std=c++17 -march=native -mtune=native
```

The CPU exposes AVX2 and AVX-VNNI to this compiler. Thread placement materially changes results because this is a hybrid P/E-core CPU.

## Test tensor and packed layouts

Real-Qwen-shaped target used throughout the native microbenchmarks:

```text
tensor identity used by the research track: blk.0.ffn_gate.weight
shape: 2560 x 9216
weights: 23,592,960
Q4_K blocks: 92,160
Q4_K bytes: 13,271,040 = 12.656 MiB
Q8_K blocks per activation: 36
standard Q8_K bytes: 10,512
Transit prepared-Q8 bytes: 9,936
```

`QK_K = 256`.

`block_q4_K` is 144 bytes: `fp16 d`, `fp16 dmin`, 12 packed scale/min bytes, 128 packed nibble bytes.

`block_q8_K` is 292 bytes: `float d`, 256 int8 quants, 16 int16 bsums.

The optimized Transit activation representation stores the same 256 int8 quants and scale but pre-combines the 16 sums-of-16 into 8 sums-of-32, for 276 bytes/block. No Q4_K weight bytes are changed or expanded.

## Numerical contract

"Exact" in this experiment means exact with respect to the packed quantized inputs and the upstream direct Q4_K × Q8_K arithmetic path. The quantization format itself is lossy relative to original floating-point weights.

The winning `explicit 4-row exact` path is bit-identical to the reproduced upstream direct path on the tested data:

```text
max_abs = 0
max_rel = 0
failures = 0
```

Some earlier accumulation variants differed from the forced-scalar reference by about `6.104e-4` because of FP32 reduction order while matching each other exactly.


The original "reference" was later found to be auto-vectorized and was not a true scalar baseline.

### V2.1 — forced scalar + integer accumulation

Artifact SHA-256:

```text
kernel_v2_1.cpp
267451f5c36f2ee7ad2382bc3684008f55937e5bc21f14a05b8a575cb51e7419
```

Key x86 instruction strategy:

```text
AVX2: vpmaddubsw -> vpmaddwd
VNNI: vpdpbusd + separate vpmulld for Q4_K scale application
```

Measured:

```text
scalar real       7.9831 ms/GEMV
AVX2 v1           2.1385
AVX2 accum         1.0925   11.31 GiB/s
VNNI v1           1.8111
VNNI accum         1.1094
VNNI 4-row         1.1123
```

Speedups: `AVX2 accum / scalar = 7.31x`; `AVX2 accum / v1 = 1.96x`.

`AVX2 accum` and `VNNI accum` were bit-identical. AVX2 won because Q4_K scale multiplication can be folded into `vpmaddwd`, whereas the VNNI form requires another integer multiply.

### Fair standalone reproduction of current upstream x86 direct dot

Artifact SHA-256:

```text
kernel_vs_llama.cpp
ea45a05242abadfefb8d6f7a1a3e796ce2293a0f2c098fe5c9f10ee43166bc38
```

### V8 — assembly audit

Artifact SHA-256:

```text
kernel_v8_asm_probe.cpp
9bd6bdeb311f069a072886f7173000e32ad2400cfd2e6af2d4b40e9c7326a09f
```

Important correction from the generated Windows x64 assembly:

- many `xmm6..xmm15` stack save/restores are ABI callee-save traffic, not evidence of hot-loop spilling;
- genuine YMM stack traffic exists in all tile widths;
- stack-frame size is not monotonic with tile width, so the 7-row collapse cannot be explained by one simple "first spill at row 7" threshold.

Approximate `constprop` stack frames observed: 4-row ~1352 B; 5-row ~1768 B; 6-row ~1240 B; 7-row ~1464 B.

### V11 — physical 4-row interleave experiment

Artifact SHA-256:

```text
kernel_v11.cpp
a4f25e15f6d4667894b9f726b4ffbbd2f1198bcc925f2f4dbefb2c006630a938
```

A one-time repack reordered the same Q4_K blocks into `block N: row0 row1 row2 row3`. No weight bytes were added.

One-time repack: `101.250 MiB in 10.715 ms`, `9.23 GiB/s payload`.

Correctness: both row-major explicit 4 and repacked explicit 4 had `max_abs=0`.

Streaming A/B/A:

```text
row-major 4-row
llama    0.9129 ms
Transit  0.7295 ms
16.94 GiB/s
speedup  1.2640x
IQR      [1.2499, 1.2723]

repacked 4-row
llama    0.9498 ms
Transit  0.7493 ms
16.49 GiB/s
speedup  1.2538x
IQR      [1.2358, 1.2980]

repacked / row-major candidate ratio = 0.9735x
```

Decision for this CPU: **reject physical 4-row repack**. The original row-major Q4_K layout is already preferable.

Because baseline frequency varies between runs, do not treat `1.2640x` as a universal coefficient. The strongest cross-cache generalization is the V10 streaming result (`1.1809x`, IQR `[1.1504,1.2031]`), while V11 demonstrates that the row-major explicit 4-row path can reach a larger paired win in a favorable run.

## What is proven

Measured on the i5-12500H:

1. AVX2 is preferable to AVX-VNNI for this Q4_K structure on this compiler/CPU because scale application fits the AVX2 madd chain better.
2. Preparing Q8_K with 8 sum-of-32 values removes repeated `bsums` work.
3. Reusing the same Q8_K activation across multiple output rows is profitable.
4. Four rows is the best stable tile in the tested 1..8 sweep.
5. Explicitly shaped 4-row code beats the generic template 4-row implementation.
6. The exact path is bit-identical to the reproduced upstream direct Q4_K × Q8_K path.
7. The speedup survives a ~101 MiB streaming working set.
8. Repacking the Q4_K weights into a physical 4-row interleave did not help this CPU.

## What is not proven

1. No end-to-end llama.cpp or Ollama token/s gain has been measured yet.
2. Current llama.cpp also contains repacked Q4_K GEMV paths; beating the reproduced direct `vec_dot` path does not automatically beat the production-selected GEMV path.
3. No all-P-core / all-core scaling curve for this exact Q4_K kernel has been measured.
4. No hardware counters have been collected yet.
5. No E5-2680 v2 / Ivy Bridge AVX-only port has been measured.
6. No NUMA-local dual-socket server benchmark has been measured.
7. The result does not implement Kimi K3 MXFP4/MXFP8 numerics.
8. The result does not yet prove full-model MoE throughput.

## Immediate integration gates

1. Patch current llama.cpp behind a separate x86 experimental dispatch.
2. Compare against whichever Q4_K production GEMV path llama.cpp actually selects for the same shape.
3. Run `llama-bench` with a real Q4_K model, fixed prompt/context, fixed threads and pinned P cores.
4. Add 1/2/4 P-core scaling with a cache-busting real-weight working set and record DRAM bandwidth.
5. Capture LLC misses, memory bandwidth, cycles/instruction and front-end/back-end stalls if a reliable Windows/Linux counter path is available.
6. Build a separate Ivy Bridge AVX/SSE/POPCNT implementation; do not compile the AVX2 laptop path for E5-2680 v2.
7. Run one process per NUMA socket with memory bound locally before composing socket rates.

## Relationship to Transit

This result does not replace the bitplane hardware path. It creates a stronger host/runtime kernel option:

```text
newer AVX2 CPU / llama.cpp Q4_K host inference:
    exact Q4_K x Q8_K explicit 4-row SIMD

old AVX-only Xeon:
    dedicated AVX/SSE/POPCNT path must be measured

Transit FPGA/tile:
    signed INT4 bitplane proof remains the hardware reference
    until MXFP4/MXFP8 or a validated Transit conversion is implemented
```

For heterogeneous MoE, the same multi-row/Q8-prep principles are directly relevant to CPU-owned routed experts because one activation vector is multiplied by many expert matrix output rows.
